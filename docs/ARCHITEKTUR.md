## 1. Leitprinzip: die Trennlinie zwischen Simulation und Darstellung

Alles in diesem Projekt hängt an einer einzigen Grenze:

```
        C++ (GDExtension)                    GDScript (Godot)
   ┌─────────────────────────┐         ┌──────────────────────────┐
   │      SIMULATION         │  ────▶  │      PRÄSENTATION        │
   │                         │  Snap-  │                          │
   │ • deterministisch       │  shot   │ • Rendering              │
   │ • Ganzzahl-Mathematik   │         │ • Touch-Input            │
   │ • 25 Ticks/Sekunde      │  ◀────  │ • UI, Audio, Kamera      │
   │ • kennt keine Pixel     │ Befehle │ • kennt keine Spielregeln │
   └─────────────────────────┘         └──────────────────────────┘
```

**Die Simulation weiß nichts von Godot.** Keine `Node`s, keine `Vector2`, kein `float` in
zustandsrelevanten Berechnungen. Sie ist eine reine C++-Bibliothek, die man losgelöst von der Engine
kompilieren und testen kann — als Konsolenprogramm auf dem Mac, in einem Unit-Test, headless in CI.

Diese Grenze ist nicht Ästhetik, sie zahlt dreifach:

1. **Determinismus** — Voraussetzung für Replays, für Savegames als Befehlsliste, und falls je
   Multiplayer dazukommt, für Lockstep-Netzwerk. Determinismus ist nachträglich fast nicht
   herstellbar, aber von Anfang an fast gratis.
2. **Testbarkeit** — Spielregeln lassen sich ohne laufende Engine prüfen. "Medium Tank gegen
   Rifle Infantry, wer gewinnt in wie vielen Ticks" ist ein Unit-Test, kein Spielstart.
3. **Performance** — der Hotpath liegt in nativem Code, ohne Sprachgrenze pro Einheit und Tick.

### Ganzzahl-Mathematik, keine Fließkomma

Aus Recherche 01: RA rechnet ohnehin in Ganzzahlen. **1 Zelle = 1024 Welteinheiten**, Winkel in
**1024 Schritten pro Vollkreis**. Das ist kein Zufall — es ist eine Fixpunkt-Darstellung mit
Zweierpotenz-Basis, also verlustfreie Bitshifts statt Division. Wir übernehmen dieses Zahlensystem
unverändert:

```cpp
using WDist  = int32_t;   // 1024 == eine Zelle
using WAngle = int32_t;   // 0..1023, 1024 == Vollkreis
struct WPos { WDist x, y, z; };
struct CPos { int32_t x, y; };   // Zellkoordinate
```

`float` ist in der Simulation verboten. Fließkomma-Rundung unterscheidet sich zwischen
CPU-Architekturen und Compiler-Optimierungsstufen — auf ARM und x86 zugleich deterministisch zu
bleiben ist mit `float` praktisch nicht zu garantieren, mit `int32` trivial.

### Datenfluss pro Frame

Die Simulation tickt mit festen 25 Hz, die Darstellung rendert mit 60+ Hz. Dazwischen wird
**interpoliert**, nicht gekoppelt:

```
Touch-Eingabe ──▶ Befehlsobjekt ──▶ Befehlspuffer ──┐
                                                     ▼
                                          Sim-Tick (alle 40 ms)
                                                     │
                                            Zustands-Snapshot
                                                     ▼
   Rendering (60+ Hz) ◀── Interpolation zwischen Snapshot N-1 und N
```

Der Renderer liest nie den Live-Zustand der Simulation, sondern immer zwei Snapshots und blendet
dazwischen. Sonst ruckeln Einheiten sichtbar mit 25 Hz.

### Determinismus-Audit (2026-09-06, für den Gleichschritt-Mehrspieler)

`docs/MULTIPLAYER.md` überträgt Befehle, keinen Zustand: zwei Geräte mit verschiedenen Compilern
(macOS-clang, Android-NDK-clang) und verschiedenen Architekturen müssen aus derselben Befehlsfolge
bitgleiche Zustände rechnen. Dafür wurde `sim/` einmal vollständig durchgesehen. Befund:

| Geprüft | Ergebnis |
|---|---|
| `float`/`double` in `sim/src` und `sim/include` | **keine** — Fließkomma steckt ausschließlich in den Render-Pfaden von `gdext/` |
| Zufall | genau ein Strom: `World::rand()` (xorshift32). Kein `std::rand`, kein `mt19937`, kein `random_device`. Seit 2026-09-06 setzbar über `World::set_rng_seed()` |
| `unordered_map` | zwei Stück (`World::index_by_id_`, `FlowFieldCache::by_goal_`), beide **nur per `find()`/`operator[]`** — nie iteriert, die Bucket-Reihenfolge kann also nicht durchschlagen |
| `std::sort` | neun Aufrufe (`economy/production.cpp` 1, `ai/bot.cpp` 8). `std::sort` ist nicht stabil; **jeder** Vergleich hat einen Zweitschlüssel (Typindex bzw. `map_.index(zelle)`) und damit eine totale Ordnung |
| Zeiger als Sortierschlüssel | keine; auch kein `std::min_element`/`max_element` über Zeiger |
| Uhr/Umgebung | kein `chrono`, `time()`, `clock()`, `getenv()` in `sim/` (die Zeitmessung sitzt in `RaSim::step`, außerhalb des Zustands) |
| Actor-Reihenfolge | Speicherreihenfolge von `actors_`; neue Actors werden hinten angehängt, Kennungen kommen aus `next_id_` |

**Zwei Funde, beide behoben:**

1. `World::step()` löste die Sichtbarkeit fest für Spieler 0 auf (`update_visibility(0)`).
   Sichtbarkeit ist aber Sim-Zustand, nicht Darstellung — `economy/production.cpp` liest
   `vis_[spy_owner]` für `InfiltrateForExploration`, `world/crates.cpp` schreibt hinein
   (RevealMap/HideMap). Auf „den örtlichen Spieler" umzustellen wäre der schlimmste Fehler gewesen:
   jeder Client pflegte dann eine andere Sichtkarte, und der erste Spion hätte die Partie gespalten.
   Richtig ist eine gemeinsame Menge: `World::set_visibility_players(uint32_t mask)`, ein Bit je
   Spielerindex, aus der Aufstellung und auf allen Clients gleich; `step()` läuft über alle gesetzten
   Bits. Einzelspieler bleibt bei `mask = 1`. Gemessen (64×64, 42 Actors, `sim/tests/run.sh`):
   eine Auflösung 4,8 µs, ganzer Tick 11,9 µs bei einem Betrachter, 13,7 µs bei drei, 15,7 µs bei
   sechs — rund 1 µs je zusätzlichem Platz, gegen 40 000 µs Budget bei 25 Hz.
2. `World::render()` setzte `RenderActor::visible` fest aus Sicht von Spieler 0. Das ist reine
   Anzeige, gehört aber trotzdem parametrisiert: `render(alpha, out, viewer)`, die Brücke gibt
   `RaSim::set_local_player()` durch. Dasselbe gilt für `gps_dots()`, `gps_active()`,
   `frozen_actors()`, `apply_frozen()`, `visibility_map()` und `drain_notifications()`.

**Bewusst offen gelassen:** `to_cell()` schiebt vorzeichenbehaftet nach rechts (`p.x >> 10`). Das ist
in C++17 implementierungsabhängig; beide Zielplattformen werden mit clang gebaut, das arithmetisch
schiebt. Sollte je ein anderer Compiler dazukommen, ist das die erste Stelle, die zu prüfen ist.

**Nicht deterministisch und das ist richtig so:** `RaSim::zap_seed_` (Tesla-Blitze) liegt in der
Brücke und zeichnet nur; Effekte, Zaps, Brandflecken und Töne stehen deshalb auch nicht im
`state_hash()`.

### Was bewusst nicht eingecheckt wird

`android/pocketra_plugin/build/`, `game/addons/pocketra_plugin/bin/*.aar` und `game/android/`
(die Android-Bauvorlage des Gradle-Baus) sind Bauergebnisse wie `game/bin/*.so` — sie entstehen aus
`tools/plugin_build.sh` bzw. legt `tools/apk_build.sh` sie bei Bedarf selbst an.

`content/` und `game/assets/` bleiben aus dem Repository heraus — beides sind EA-Assets bzw. daraus
abgeleitete Dateien. Das Repository enthält **nur eigenen Code und die Pipeline, die die Assets
erzeugt.** Jeder, der das Projekt baut, lädt sich den Content selbst (siehe Recherche 01, §7) und
lässt die Pipeline laufen. Das hält die rechtliche Lage sauber und das Repository klein.

## 3. Der Actor-Aufbau: Komposition, aber schlanker als OpenRA

OpenRAs Trait-System (Recherche 01, §3) ist konzeptionell richtig — Verhalten als Komposition statt
Vererbung — aber mit **571 Trait-Klassen** massiv überdimensioniert für das, was wir bauen. Es ist auf
beliebige Mods über vier verschiedene Westwood-Spiele ausgelegt. Wir brauchen ein Spiel.

Der Mittelweg: **Komposition mit festem Komponentensatz** statt offenem Trait-Registry.

```cpp
struct Actor {
    ActorId       id;
    ActorTypeId   type;        // Index in die Regeltabelle
    PlayerId      owner;
    WPos          pos;
    WAngle        facing;
    int32_t       health;
    ComponentMask components; // Bitmaske: welche Komponenten aktiv sind
};
```

Komponentendaten liegen in **parallelen Arrays** (`std::vector<Mobile>`, `std::vector<Turret>`,
`std::vector<ProductionQueue>`, …), indiziert über eine Zuordnungstabelle — nicht als Zeiger im Actor.
Das ist cache-freundlich: Der Bewegungs-Tick iteriert linear über alle `Mobile`-Komponenten, statt
hunderten Zeigern durch den Heap zu folgen. Bei 500 Einheiten × 25 Ticks/s macht das den Unterschied
zwischen "unmerklich" und "Hitzeentwicklung".

**Die Conditions aus OpenRA übernehmen wir** — String-Tokens, die Komponenten aktivieren und
deaktivieren (`damaged`, `parachute`, `cloaked`, `powerdown`). Das ist der Mechanismus, der Veterancy,
Iron Curtain, Stromausfall und Tarnung ohne Sonderfälle im Kerncode löst. Nur als `uint32`-Bitmaske
statt als Strings.

## 3a. Spiellogik: OpenRA ist die Referenz

Seit 2026-09-02 gilt: **Alle Spiellogik wird an OpenRA ausgerichtet** — Toms Fork
[tarek369/OpenRA](https://github.com/tarek369/OpenRA), lokal als Shallow-Clone unter `reference/OpenRA/`
(gitignored, GPL). Vor jeder neuen Regel wird die OpenRA-Stelle gelesen und im Code referenziert.

Der Grund ist erlebt, nicht theoretisch: Die erste, selbst erfundene Ankunftsregel für Gruppenbewegungen
brauchte fünf Iterationen und war immer noch fehleranfällig. OpenRAs `Move.cs` hat für jeden Fall
(zu nah, blockiert, wartend, ausweichend, aufgebend) eine erprobte Antwort.

Einrichtungsseite die aus dem CD-Abbild behaltenen Archive (`scores.mix`, `movies1.mix`/`movies2.mix`,
bei der deutschen CD zusätzlich `speech.mix`/`sounds.mix`). Bei Sprache Deutsch wird die deutsche CD
zuerst geöffnet: das zuerst geöffnete Archiv gewinnt bei gleichem Namen (Sprachausgabe, Cameos).
Bis 2026-09-06 kannte `archives()` nur `mix/` — Original-Musik und Filme der CD lagen zwar auf dem
Gerät, wurden aber nie gefunden (Toms Handtest, Punkt 2).

**Musik ist zustandsabhängig, nicht einmalig**: `Music` (Autoload) baut seine Titelliste in
`rebuild()` und wird nach jeder Änderung an den Spielinhalten neu gerufen (Einrichtung fertig, CD
gelöscht, alles gelöscht, Quelle umgeschaltet). Vorher stand die Liste seit dem Autoload-Start fest,
eine frisch eingerichtete CD spielte also erst nach einem Neustart der App. Die Quelle
(`scores.mix` der CD / Ordner `original/music` / eigene Stücke) steht in `user://settings.cfg`
(`[audio] music_source`), die Anzeigenamen in `assets/rules.json` unter `music.title`
(aus `mods/ra/audio/music.yaml`).

Geprüft wird gegen die Python-Pipeline, Byte für Byte: `gdext/tests/run.sh` vergleicht
MIX-Verzeichnis (48 Archive, 5558 Einträge), 1095 SHP/TMP, die Paletten, alle drei Atlanten gegen
`game/assets/atlas`, den Cameo-Atlas, AUD gegen ffmpeg und den VQA-Kopf. Der Gesamtlauf auf dem
Gerät hängt an `Godot --headless --path game -- --test-content`; am Mac (M4 Pro) braucht er
13–23 ms für die Archive, 115–172 ms für alle drei Atlanten, 35–44 ms je Soundsatz.

### Aktualisierung ohne neue APK (2026-09-04)

Toms Wunsch: Freunde sollen nicht ständig eine neue APK bekommen. Zwei Stufen, streng getrennt:

**Stufe 1 — das Paket.** `game/export_presets.cfg` hat zwei Presets, die nie als APK exportiert
werden, sondern nur mit `--export-pack`: `Update-Paket` (dieselbe Dateimenge wie „Android
Verteilung", also ohne die EA-Inhalte, zusätzlich ohne `bin/**`) und `Update-Paket schlank` (ohne
`assets/music|ui|intro`, ~39 statt ~116 MB). `tools/update_pack.sh` baut das Paket, rechnet SHA-256
und schreibt `build/update/version.json`; `--upload` schiebt Paket, APK und danach die Versionsdatei
per rsync auf Toms Webserver (reine statische Dateien, kein Serverskript).

**Stufe 2 — der Ablauf in der App.** Der Autoload `UpdateBoot` steht ganz oben in `project.godot`
und hängt `user://update/current.pck` schon in seinem `_init()` ein — vor Lang/Names/MusicPlayer und
vor der Hauptszene, denn `ProjectSettings.load_resource_pack(path, true)` wirkt nur auf das, was
danach geladen wird. Deshalb ist dieser Bootstrap absichtlich winzig und kennt nur das Einhängen und
den Vergleich `min_extension` ≤ `RaSim.version()`; die eigentliche Logik (`update_config.gd`,
`update_service.gd`, `update_page.gd`) kommt aus dem Paket und ist damit selbst nachbesserbar.
`UpdateService` hängt im Hauptmenü, holt `version.json` nicht blockierend, lädt bei größerer
`pack_version` nach `next.pck`, prüft die Prüfsumme und benennt um.

**Grenzen** (im README ausführlich): `update_boot.gd` und `project.godot` (Autoloads, Übersetzungs-
liste, Hauptszene, App-Version) kommen immer aus der APK; die native Extension wechselt nur mit der
APK, wofür jedes Paket `min_extension` trägt; der Neustart nach dem Download ist auf Android nur ein
Hinweis (`OS.set_restart_on_exit()` wirkt dort nicht).

**Stilllegen.** `version.json` kennt `min_supported` (App-Version) / `min_supported_pack` und
`disabled: true`. Trifft eines zu, merkt sich die App das in `user://update/state.json` und zeigt
beim Start die nicht wegdrückbare Sperrseite (`UpdatePage`) — auch offline. Eine Kopie, die den
Server nie erreicht hat, lässt sich prinzipbedingt nicht stilllegen.

## 4. Pathfinding: Flow Fields, nicht A* pro Einheit

Die teuerste CPU-Last im RTS. Bei 200 Einheiten mit einzelnem A* pro Einheit und Neuberechnung bei
Blockade ist ein Handy chancenlos.

**Ansatz:** Ein Bewegungsbefehl an eine Gruppe erzeugt **ein** Flow Field zum Ziel — ein Raster, in dem
jede Zelle die Richtung zum Ziel speichert. Alle Einheiten der Gruppe lesen daraus. Kosten sind
unabhängig von der Gruppengröße; ein Feld für 5 oder 200 Einheiten kostet gleich viel.

- Grobes Feld über die ganze Karte (einmal pro Befehl), lokale Ausweichlogik zwischen Einheiten
  darüber gelegt.
- Felder werden **gecacht** und geteilt: gleicher Zielbereich = gleiches Feld.
- Neuberechnung **amortisiert** über mehrere Ticks, nicht alles in einem.
- Terrainkosten pro Zelle aus dem Tileset (Straße schneller, Wasser für Landeinheiten gesperrt) —
  RA hat diese Daten bereits, siehe Recherche 01, §4.

Einzelnes A* bleibt als Rückfallebene für Einzeleinheiten auf kurzer Distanz.

## 5. Rendering: ein Draw Call für alle Einheiten

Aus Recherche 01, §5 und Recherche 02: palettenindizierte R8-Texturen plus Palettenlookup im Shader.

- **Ein Texturatlas** pro Kategorie (Infanterie / Fahrzeuge / Gebäude / Effekte), `FORMAT_R8`.
- **Eine Palettentextur** 256×N RGBA8, eine Zeile pro Spieler, Indizes 80–95 mit der Spielerfarbe belegt.
- **`MultiMeshInstance2D`** mit `use_custom_data`: pro Instanz ein `vec4` mit
  (Atlas-U, Atlas-V, Frame-Index, Spielerzeile). Tausende Sprites, ein Draw Call.
- **`filter_nearest` auf beiden Texturen** — zwingend. Lineare Filterung interpoliert zwischen
  *Palettenindizes*, was zu zufälligen Farben führt. Der häufigste Fehler bei diesem Verfahren.
- Index 0 → `discard`. Index 4 → Schatten, schwarz mit ~55 % Alpha.
- Palettenrotation für Wasser und Erz: betroffene Einträge pro Tick in der Palettentextur zyklisch
  verschieben.

Die Facing-Auflösung braucht **die nichtlineare 32-Facing-Tabelle** aus Recherche 01, §4 —
ohne sie snappen alle Fahrzeuge sichtbar falsch.

## 6. Reihenfolge des Aufbaus

Bewusst so sortiert, dass die **riskantesten Annahmen zuerst** geprüft werden. Jede Stufe beantwortet
eine Frage, die alles Nachfolgende trägt.

| # | Meilenstein | Beantwortet die Frage |
|---|---|---|
| **0** | Toolchain: Godot 4.7.2 + JDK 17, leeres Projekt aufs echte Gerät exportieren | Läuft der Android-Export überhaupt auf diesem Mac? |
| **1** | Leere GDExtension in C++, kompiliert für arm64, auf dem Gerät geladen | Trägt der GDExtension-Pfad? *(Recherche 02, offener Punkt)* |
| **2** | Asset-Pipeline: MIX entpacken, ein SHP → R8-Atlas, im Shader palettiert anzeigen | Funktioniert das Palettenverfahren wie angenommen? |
| **3** | **Gestenprototyp** auf dem Gerät: Tilemap, 50 Dummy-Sprites, volles Gestenvokabular, kein Gameplay | Ist das Steuerungskonzept aus Recherche 03 tragfähig? |
| **4** | Simulationskern: Karte, Bewegung, Flow Fields, 200 Einheiten laufen | Hält die Performance bei realistischer Einheitenzahl? |
| **5** | Kampf: Waffen, Projektile, Schaden nach `rules.ini`, Zerstörung | — |
| **6** | Wirtschaft: Erz, Harvester, Raffinerie, Credits, Strom | — |
| **7** | Bauen: Bauqueues, Prerequisites, Platzierungsmodus, Techtree | — |
| **8** | HUD: Bauleiste, Minimap, Radialmenü, Kontrollgruppen | — |
| **9** | Gegner-KI, Skirmish-Match gegen den Computer | — |

**Stufen 0–3 sind die eigentliche Risikophase.** Sie enthalten kaum Spiellogik, prüfen aber jede
Annahme, auf der die Architektur ruht. Erst wenn ein Panzer-Sprite mit korrekter Teamfarbe auf dem
echten Gerät steht und sich per Rahmenauswahl anfassen lässt, ist der Rest überwiegend Fleißarbeit
mit bekanntem Ausgang.

Wenn Stufe 3 zeigt, dass das Steuerungskonzept nicht trägt, wurde noch nichts gebaut, was davon
abhängt. Das ist der Sinn der Reihenfolge.

## 7. Offene Architekturfragen

- **Savegames** — Snapshot des kompletten Simulationszustands oder Befehlsliste ab Spielstart?
  Befehlsliste ist kleiner und fällt bei Determinismus gratis ab, macht aber das Laden langsam
  (Neusimulation). Vermutlich beides: Snapshot alle N Ticks plus Befehle dazwischen.
- **Kartenformat** — OpenRAs `.oramap` übernehmen, RAs originales `.mpr` lesen, oder ein eigenes?
  Für den Anfang reicht ein eigenes, einfaches; Originalkarten zu lesen ist ein späterer Komfortgewinn.
- **Multiplayer** — vorerst außen vor, aber die deterministische Simulation hält die Tür offen.
  Keine Architekturentscheidung dafür jetzt, nur keine, die es verbaut.
- **Wie viel `rules.ini` vs. wie viel OpenRA-YAML** in die Regeldaten einfließt — Recherche 01, §9
  empfiehlt `rules.ini` für Balance und OpenRA für Sequences. Die Grenze wird sich beim Bau von
  `tools/rulesconvert/` konkretisieren.
